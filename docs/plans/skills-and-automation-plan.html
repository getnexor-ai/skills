Why four withdrawals

The repo's own contribution rule — “no customer names, no personal data, no production statistics, no credentials, no internal file paths” — was applied to content. This audit applies it to capability: a skill is withdrawn when publishing it hands a stranger operational knowledge of Nexor's production systems, even with every name scrubbed.

SkillVerdictReason it cannot stay public
query-catalogWithdraw 455 lines of canonical SQL over the production schema — a complete map of table and column names. The transferable idea (a canonical-query catalog per metric) survives as one paragraph; the content is 95% Nexor's database.
quick-meetingWithdraw Documents that the production booking endpoint accepts internal writes with only a client-id header and no user token. Even with the hostname redacted, that discloses the auth model of a prod write path.
webchat-incidentWithdraw Names the abuse-defense blind spots — the fingerprint detector requires letter+digit suffixes, and the honeypot layer that catches 100% of historical attacks “costs one line to evade.” Publishing your defenses' gaps is a gift to the next attacker.
nexor-onboardWithdraw An internal operator tool: its scripts read the production DB with a service-role key that bypasses RLS, and its outputs are client lists. The public funnel concept (T0→T4) is already summarized in the skill prose; the tool itself has no public user.
Mechanics already in place. Withdrawal is one line per skill in package.json → nexorSkills.unpublished plus a matching files negation. The CI gate (scripts/prepublish-check.mjs) then hard-fails any build where one of these files would reach the tarball — the same mechanism that already withholds agent-browser. The skills stay in the repo for internal agents.

The six primitives, and the ladder that orders them

Everything a client asks for lands on one of six primitives. The skill's core claim: config beats code — config is operator-visible, editable in the UI, and cannot crash; code is invisible to operators and yours to maintain forever. Descend the ladder only when the rung above cannot express the requirement.

3Background jobcron · event · api (forced)NoFiltered cohortJob config: filters + steps + actions
4Cloud functionA lead.* eventJSOne lead per eventSandboxed worker, effects buffer
5Scheduled functioncron + timezoneJSCohort (lookup query)Sandboxed worker, effects buffer
6Workflow transferStatus with transfer_config reachedNoOne leadStatus config; chain snapshot carried
1
Can the agent do it in conversation?
A status, a required field, a stage-gated tool, a prompt rule → agent config. “Notify us when budget > X” is usually just a tool call in-turn.
2
Is it a standard lifecycle nudge?
Booking confirmations, pre-meeting reminders (signed delay_minutes vs event_start), host notifications, stale-lead recontact → rules. Configure and stop.
3
Is it expressible as “filter leads → condition → action”?
Job step vocabulary: evaluate_metadata / evaluate_field / evaluate_tag (date-in-tag) → actions send_message (approved template, then_status_key for send-once), set_lead_status, assign_workflow, workflow_transfer, enrich_lead → background job. Always set max_leads_per_cycle (≤500) + cooldown_minutes; dry-run anything that messages humans.
4
Does it need custom logic?
Branching, computation, or an external API the job vocabulary can't express. Trigger grammar routes it: “when a lead …” → cloud function (event, one lead). “every morning / Monday …” → scheduled function (cron, cohort). A “when” that tolerates a day of latency across many leads → prefer the scheduled sweep (dry-run shows the whole cohort first).
5
Does the lead need a different agent?
Goal / persona / cadence / channel mix changes fundamentally → transfer. If both “agents” would share 80% of their prompt, it's one agent with more statuses.

Part 2 · Automation architecture

Cloud vs scheduled functions — the semantics that decide designs

Both run tenant JS in an isolated sandbox and buffer effects instead of mutating directly. Every effect is scoped to the function's own client; a foreign lead id no-ops. One failed effect is recorded without aborting the rest. From there, the two types diverge on purpose:

Cloud function event · one lead

  • Triggers (6): lead.created, lead.updated, lead.status_changed, lead.assigned, lead.tag_added, lead.unsubscribed
  • ctx: the lead + the event; effects default to that lead
  • No chaining: assignLead does not re-emit events — the recursion guard exists because lead.updated → updateLead → ∞. A design that needs chained events is a scheduled function.
  • Manual test runs are dry-run by default — effects previewed, not applied
Use when: enrich a new lead via external API · recompute a score on field change · mirror a status into the client's CRM · react to an unsubscribe.

Scheduled function cron · cohort

  • Trigger: cron_expression + timezone; cohort pre-resolved by a lookup query into ctx.leads; capped by max_leads_per_cycle
  • Every effect names its own lead — there is no “the” lead
  • Chaining allowed: assignLead intentionally re-emits lead.assigned/lead.updated — a sweep can assign and let a cloud function react per-lead
  • Manual runs always dry-run: candidates found + effects previewed. Read that list before activating anything that messages people.
Use when: nightly re-scoring · weekly digests · “follow-up date arrived” sweeps · data hygiene passes.
Shared effects API (both types): updateLead · updateMetadata · upsertLead · setLeadStatus · assignLead · assignToWorkflow · tagLead · deactivateWorkflowRun · updateEnvironmentVariable

Transfers — the agent-to-agent contract

  • Fired by: a status carrying transfer_config → target_workflow_id; or cohort-scale via a job/function action.
  • What the platform does: cancels source cadence, deactivates the source run (outcome='transferred'), creates a fresh target run, reassigns the conversation thread, accumulates a transfer chain with a snapshot of source fields (multi-hop: C sees A's and B's fields).
  • Fields do not copy into target field values — schemas differ by design; the target agent reads the chain snapshot.
  • First contact: AI transition message when the messaging window is open (contextual handoff composed by the target agent), else the target's hot-contact template. Never also aim a “welcome” job at freshly-transferred leads — the handoff already speaks.
  • Fresh-run rule: A→B→A is safe (no zombie runs) but every hop restarts cadence — if the “transfer” is a stage of the same conversation, it's a status, not a transfer.
The five anti-patterns the skill encodes: a function that a rule already was · an event function relying on its own re-trigger (the guard silently eats step 2) · cohort messaging without then_status_key/cooldown (re-sends every cycle) · transfers used as pipeline stages · activating cohort automations without reading the dry-run.

Use case → exact configuration

The worked mappings the skill ships as templates. Column three is deliberately concrete: the deliverable of the skill is a configuration, not a recommendation.

Client asks for…PrimitiveExact configuration
“After every completed meeting, send a satisfaction survey — once.” Job Cron daily · workflow filter on post-meeting status · action send_message (approved template) with then_status_key: surveyed. Send-once is stateful, never assumed.
“Remind the lead the day before and the morning of the meeting.” Rules Two reminder rules on event_start: delay_minutes −1440 and −180. Nothing else — not a cron, not a function.
“When a lead fills in company size, enrich from our API and score them.” Cloud fn lead.updated · guard on the field actually changing · external fetch · updateMetadata + tagLead. Code earned by the external call + computation.
“Every Monday, re-activate leads whose ‘call me in N weeks’ date arrived.” Job → Sched fn First try config: evaluate_field date_before_today in a job. Only if the date needs computing: scheduled fn, cron 0 9 * * 1, lookup on the parked status, setLeadStatus per lead.
“Once qualified, a different flow schedules the demo with its own cadence.” Transfer transfer_config on the qualified status → target workflow. Target agent reads budget/need from the transfer chain; its cadence + prompt take over; AI transition handles the handoff message.
“When a lead unsubscribes anywhere, flag them in our CRM.” Cloud fn lead.unsubscribed → CRM HTTP call. An agent tool is wrong here: unsubscribes also happen outside conversations.
“Send this campaign once, when we say go.” Job (api) trigger_type: api + forced run. Stays visible, auditable, re-runnable — never a one-off script.
“One sales conversation with contacted / qualified / booked stages.” One agent Statuses on a single workflow. Three agents here is the canonical mistake: every hop resets cadence and fragments history.

Where this lands

  • Skill shipped: skills/automation-architecture/SKILL.md — registered in marketplace.json (agent-playbooks), passes the publish gate (34 on disk, 33 publishable).
  • Distribution: next merge to main publishes it in @nexor/skills; the master-editor and dashboard agents receive it through the same sync as every other skill.
  • Next iteration (recommended): a trigger eval for its description (the webchat-incident EVAL.md method — positives: “when should I use a scheduled function”; negative controls: pure prompt edits, single reminder asks), and a worked-example eval that feeds it three raw use cases and grades the configurations against this table.
